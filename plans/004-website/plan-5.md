# Phase 5 — Publish

Put the site online, keep it from rotting, and document how it is maintained.
Depends on phase 4 (or on phase 2, if publishing earlier is preferred — the
workflow does not care which pages exist).

## Tasks

### 5.1 Site completeness

- `404.html` — the same chrome, a short "no such page" body, and the nav. GitHub
  Pages serves it automatically for unknown paths.
- `favicon.ico` or a small `favicon.png` referenced from `head.html`. This is
  the one image the design permits; if there is no artwork, ship no favicon
  rather than a placeholder.
- `robots.txt` allowing everything, so the absence of one is a decision rather
  than an oversight.
- No sitemap, feed, or `og:` metadata — out of scope per the design.

### 5.2 Link and markup checking

Extend `t/web/site.t` into the site's real gate:

- Every internal `href` and `src` resolves to a file in `$(WEBOUT)`, including
  fragment targets (`#fugulib`) — an `id` that does not exist is a broken link
  the browser will not report.
- No page links to a path outside `$(WEBOUT)` or to `file://`.
- Every built page is reachable from `index.html` by following links; an
  orphaned page is a page nobody will find.
- External links are collected and reported but **not** fetched: the design says
  the build touches no network, and that must hold for the test too.
- Assert `$(WEBOUT)` contains only the expected file types — no `.man/` staging,
  no editor backups, no stray sources.

### 5.3 CI

- A `website` job in `.github/workflows/check.yml`, or a new `web.yml`,
  installing `mandoc` and `lowdown`, running `make web`, and running
  `t/web/site.t`. Fast enough (seconds) that it needs no caching.
- A deploy job on pushes to `main` only: `make web`, then
  `actions/upload-pages-artifact` over `$(WEBOUT)` and `actions/deploy-pages`.
  Pull requests build and check but never deploy.
- Least privilege: `permissions: contents: read, pages: write, id-token: write`,
  set on the deploy job alone and not at workflow level.
- Enabling GitHub Pages with the "GitHub Actions" source is a one-time repo
  setting that must be done by hand; the workflow cannot do it and will fail
  confusingly until it is. Note this in the phase's commit message.

### 5.4 Custom domain

Decide before deploying, because it changes what gets committed:

- Default: publish at `https://<owner>.github.io/openhap/`. **A project-path URL
  breaks a flat site's assumptions only if any link is root-absolute** — every
  link in this design is relative, so it works unchanged. Verify that claim
  rather than trusting it.
- With a custom domain: a `CNAME` file in `$(WEBOUT)`, generated by the `web`
  target so it survives every rebuild, plus DNS. Do not hand-commit a `CNAME`
  into the deployed branch — there is no deployed branch to commit it to.

### 5.5 Documentation

- `web/CLAUDE.md` — how the build fits together, what the two scripts do, how to
  add a page, and the two recorded limitations: `pod2man` drops `L<>` links
  (phase 4), and whatever phase 2 concluded about mandoc's two-template `man=`
  behaviour. It points at the man pages and the design; it does not restate
  them.
- `README.md` — one line linking to the site, near the top.
- Root `CLAUDE.md` — the placement table's row 1 gains the website: `web/`
  _presents_ `README.md`, `INSTALL.md`, and `man/` and never restates them, and
  only site-specific framing lives in `web/*.body.html`. Without this the next
  contributor has no rule telling them not to write install instructions into
  `index.body.html`.
- `make help`, if one exists, or the Makefile's target list — mention `web`.

## Deliverables

- `web/404.body.html`, `web/robots.txt`, optional favicon
- `.github/workflows/` — build/check job and Pages deploy job
- `Makefile` — `404.html`, `robots.txt`, optional `CNAME`
- `t/web/site.t` — link, reachability, and cleanliness checks
- `web/CLAUDE.md`, `README.md`, root `CLAUDE.md`

## Acceptance criteria

- A push to `main` publishes the site; the published pages match a local
  `make web` byte for byte.
- A pull request builds and checks the site and deploys nothing.
- `t/web/site.t` fails on a deliberately introduced broken internal link, a
  dangling fragment, and an orphaned page — each verified by introducing the
  fault, not assumed from reading the code.
- The site works from a project-path URL with no root-absolute links anywhere.
- An unknown path serves `404.html` with working navigation.
- The whole site loads with no network requests beyond the pages themselves: no
  fonts, no scripts, no third-party anything.
- `make check` stays green.
